## 一、总评

**设计上站得住、不用推翻的部分**
- 主线是对的：function 为主、资产为底座、上下文里只放引用、闸门放在花钱之前、人审本身也是一个 function。
- 多数「事故 → 修复」修在机制层，而不是提示词层，这是正确的方向。例如引用门、模型锁、缺段不成片、占位符拒收、批量工具计次。
- 人审挂起/恢复时历史消息始终合法：同一迭代只挂第一个，其余按失败回填，先回填决策再修补。次数口径在单进程内没有竞态。MCP 有白名单，默认 L-external。路径都在 resolve 之后判断，`..`、大小写、ADS、junction 都绕不过去。
- 性能暂时不是问题：1136 份资产全量加载约 0.4 秒，按集查询在毫秒级。

**绝大多数真实故障来自 7 个系统性缺口**

| # | 缺口 | 一句话 | 典型后果 |
|---|---|---|---|
| A | 没有「项目/剧」维度 | 资产、记忆、预算、锚点、面容、流水线都按「全库最新」或「会话」取 | 串剧：新剧显示「已有 79 集」、1–5 集「已有跳过」；/auto 会用旧剧的资产库渲新剧 |

## 二、分环节问题清单

### 1. 开工与会话（CLI 启动、产线、预算、产物目录、快照）

- **[P0] 开工前不确认预算，你定的规则没落地。** 证据：`interfaces/cli/main.py:568-681` 启动流程里没有这一步；这份副本里没有 TaskBudget；CostGuard 也不按视频秒数计（`harness/model/budget.py:58-62`）。改法：选完产线后，确认「金额 / 段数 / 视频秒数」三项上限，写进快照，每次开工复用或重确认。
- **[P0] 产物目录被 default 会话的快照覆盖，不是「当前文件夹」。** 证据：只要快照里有 `output_dir` 就覆盖 cwd（`main.py:620-623`）；不带 `--session` 时会话名一律是 default（`app.py:342`）；当前的 default.json 里是 `E:\西游记`，面板却仍写「当前文件夹」（`main.py:657-658`）。后果：换任何文件夹启动，产物、清点、本地素材 pin 和 `.drama-state.json` 都指向西游记。改法：没有显式传 `--session` 时以 cwd 为准；和快照不一致就问一次；会话名和台账 project 都从产物目录派生。
- **[P1] 未命名的会话共用 default 快照**（`app.py:342,353-360,391`；`main.py:615`）。在 B 文件夹做海报时，会装回 A 文件夹短剧的最近几轮、模型锁和「当前产线=短剧」。
- **[P1] 产物目录的回落判断在 Windows 上不可靠。** `domain/output.py:44` 的 `os.access` 对目录恒为真，System32 也是 True；`:42` 只用等号判断「是不是项目目录」，在 src、workspace 子目录里启动不会回落；在家目录启动会把 AppData 扫进本地素材。
- **[P2] 快照不是原子写，写失败也不报**（`capabilities/memory/session.py:73-85,135-155`）。

### 2. 主循环与上下文

- **[P1] 估算不含工具 schema，历史轮又被校准了两次。**
  - 实测：89 个工具的 schema 共 4.4 万字符，约 1.47 万 token，每次请求全量发送；首轮消息估算才约 3.3K。
  - 乘法校准的比值因此被夹到 3.0（`harness/context/assembler.py:129-135`）。`loop.py:372` 已经校准过一次，`assembler.py:151` 又乘一次。
  - 后果：历史轮的折叠阈值实际降到约 700 token，上一轮超过 800 字的工具结果只剩 200 字开头，模型只好反复 read。日志里重复 read_asset 14/134 次，校准系数触到过 3.0。
  - 改法：工具 schema 作为加性常数计入估算；历史轮直接用 `t.tokens`，不再乘校准。
- **[P1] 按 token 驱逐时累加的是未折叠原文，而且没有回差**（`harness/context/window.py:77-80,91-92`）。一旦超过 12 万，之后每轮都会剔掉最老一轮：缓存每轮被打穿，外加每轮一次 memory_extract。改法：按折叠后的视图计 token，超限时一次剔到低水位（60–80K）。
- **[P1] 两级披露对内置工具没有生效。** 89 份 schema 全量随请求发送，工具目录又在系统提示词里列了一遍（`assembler.py:187-191`）。`load_tool_schema` 展开的 schema 当轮不生效（`loop.py:234-235`）。演示工具 sleep_demo、publish_demo 进了生产工具目录（`harness/tools/builtin.py:110-152`）。
- **[P1] 默认工具超时 120 秒，比工具内部的模型调用还短。**
  - drama_write、drama_expand、reference_to_shots 等工具没声明 timeout，而 gemini 自己的超时就是 300 秒（`harness/tools/dispatcher.py:33,72`；`config/models.yaml:92,162`）。
  - 日志里有 19 次「工具执行超时」。超时只取消本地协程，远端照跑、照扣费。模型还把它误诊为「服务端故障」，转去手写分镜，直接引出了占位符事故。
  - 改法：会调模型或媒体的工具，注册时强制声明 timeout。
- **[P1] 中断时，同一批里已经完成的工具结果全丢。**
  - TaskGroup 要等全部任务结束才收集结果（`dispatcher.py:66-81`），补记文案又固定写成「没有执行结果」（`loop.py:134-138`）。
  - 后果：6 段视频完成 4 段时按 /stop，这 4 段已经计费，但模型以为没做，下一轮又生成一遍。
  - 改法：完成一个就回填一个；补记文案改成「可能已产出，先核对资产」。
- **[P1] 超时被当成连接错误重试 6 次，CLI 还会再续跑 3 次。**
  - openai SDK 里 `APITimeoutError` 继承自 `APIConnectionError`（`harness/model/gateway.py:280-284`、`config.py:61-64`、`loop.py:71`、`main.py:358`）。
  - 单次超时会随上下文放大到 540 秒，最坏情况下整包重发 24 次。
  - 改法：超时只重试 1–2 次，并且先压缩上下文再发。
- **[P1] finish_reason 全链路没有人消费**：gateway 里有这个字段（`gateway.py:333`），但主循环、drama、视觉门都不看。
  - 输出被截断（length）时，参数不完整，只会报「不是合法 JSON」，模型原样重试。
  - 内容过滤（content_filter）返回的空回复被当成正常完成。
- **[P2] continue_turn 有四处遗漏**：不修补悬空调用、不校验是不是最新一轮、丢掉召回的记忆、不做驱逐（`loop.py:522-544`）。
- **[P2] L0 内核认识领域。** `DEFAULT_SYSTEM_PROMPT` 写满了短剧、抖音和 drama_* 工具名（`assembler.py:37-92`），里面「一集六段视频」的说法也已过时；`loop.py:87,426` 按「剧本/第N集」判断节点大小。import-linter 只查 import，查不出字符串里的领域知识。改法：系统提示词和环节规则由 L2 通过构造参数注入。
- **[P2] 其他零散问题。**
  - 单次迭代内的工具并发没有上限。
  - reasoning_content 被丢弃（`gateway.py:326-335`），要核实 K3 是否要求回传。
  - ExecutionRouter 只剩测试在用，GraphRuntime 只挂在 `agent graph` 子命令上，两套人审和护栏语义要并行维护。

### 4. 短剧 · 分镜（drama_storyboard）

- **[P0] /auto 把 5 集并成一次分镜调用，必然被截断。**
  - 调用处在 `domain/pipeline/episode_pipeline.py:313-317`。每集至少 68 行、通常 80–120 行（`domain/drama/format.py:83-93`），5 集远超输出上限 32768 token（`config/models.yaml:158`）。
  - 截断后解析失败，这一批被标记失败、永不重派，流水线就卡在这里（`episode_pipeline.py:318-320,366-368`）。修订时还会把截断的输出整段发回去（`drama.py:1797-1811`）。
  - 改法：按单集调用；检查 finish_reason=length，截断就续写。
- **[P0] drama 三个工具只收全文，收到垃圾输入会编内容。**
  - `drama.py:247-262,280-296` 只收全文，手动链会让模型把整部剧塞进工具参数，这正是 25 万上下文和折叠占位符两起事故的共同入口。

- **[P1] 截断和内容过滤都只报「JSON 解析失败」**（`drama.py:1761-1764,1824-1833,1926-1929`）。遇到 length 应该续写；遇到过滤应该明确报原因，不自动重试。

### 5. 短剧 · 资产库与参考图（drama_assets / drama_render_assets / 面容审查）

- **[P0] `render_assets(only=…)` 生成的新包会盖掉完整包。**
  - 新包只含本次请求的类别（`drama.py:2244-2274,2363-2376`），而下游默认取最新的包（`drama.py:2201-2208`）。代码注释写着「实测模型先 only=characters 省钱，之后再补」，说明这种调法真实发生过。
  - 后果：按覆盖率提示补跑 only=scenes 后，渲视频会被引用门拦下；再跑 all 会重新生成主形象，既换脸又重复付费。
  - 改法：先完整复制上一个包，只覆盖新生成的键。
- **[P1] 渲视频时从来不传主形象。**
  - `bind_costumes` 把裸角色名全部换成服装 ID（`domain/drama/wardrobe.py:43-45,55-57`），渲染时只传服装全身图（`drama.py:2641-2655`）。
  - 全身图里脸只占一小块，身份门又拿全身图去比 384px 的低清帧。这很可能就是「参考图传了照样漂」的主因之一。
  - 改法：每个人物同时传「主形象（脸）+ 服装图」，并在提示词里写明哪张是脸。
- **[P1] 真实感规则不分年龄。**
  - 所有人物都被加上 attractive / RAW / 毛孔并补瑕疵描述（`domain/realism.py:113-128,398-414`），和 8 岁女主被儿童护栏拒绝的事故对得上（因果关系属推测）。
  - 主形象被拒后，该角色的全部服装都被连带跳过（`drama.py:2311-2316`），没有降级路径。
  - 档位也有冲突：`realism.py:517-521` 的「必须保留少量雀斑」不分档位，`prompts.py:81` 的「必须含皱纹」和 subtle 档矛盾。
- **[P1] 面容审查的候选范围太宽。**
  - 只要摘要里带角色名就算候选（`drama.py:1399-1411`），「场景·陆离的公寓」也会被算进来。
  - 被判为不一致后，场景条目的 url 被换成人像，kind 却仍是场景（`drama.py:1567-1569`）。
  - `superseded_by` 写了，但全仓库没有读取点。
- **[P1] 换脸不会传播。** 用 drama_use_local_ref 或 repin 换了主形象后，服装图仍按名字复用（`drama.py:2270-2274`），新脸到不了视频。改法：主形象一变，派生的服装图同步失效。
- **[P2] 托管失败时退回「复刻」**：重新生成一张图，不过任何门（`drama.py:1224-1247`），可能换脸。

### 6. 短剧 · 视频提示词（drama_shots）

- **[P1] 全角括号让场景引用失效。** 提示词示例里场景写成全角「（奢华酒店顶层客厅）」（`domain/drama/prompts.py:203`），解析只认半角（`domain/drama/models.py:263`）。模型照着示例写，场景参考图和按场景换装就全部失效（`wardrobe.py:19-22`）。另一边，用子串匹配角色名时，「(OS)」这类标注会被当成资产引用，preflight 整批误拦（`drama.py:3008-3013`）。
- **[P1] 换视频模型后，时长被静默截断。** 时长会被截到新模型的 max_duration（`domain/functions/media.py:718-719`），而时间线和一集 240 秒仍按每段 15 秒算，成片只剩约 2/3，全程没有提示。改法：锁定的模型一变就重新规划 shots，或在渲染前拦下。
- **[P2] 提示词叠得太厚，而且互相矛盾。**
  - 外层包装约 2000 字，描述本身只有 400–800 字，四段都自称「最高优先级」或「硬性」。
  - `prompts.py:182` 写「废除时间轴」，`domain/media/fast_cut.py:45-47` 却注入时间线；`:190` 写 10–14s，`format.py:187` 写 10–15s。
  - 没有校验「[切镜] 数量 = cuts 数量」。

### 7. 短剧 · 渲染与质检门（drama_render_shots）

- **[P0] 门链会让带字幕、变脸的片段进成片。**
  - 顺序是 身份 → 字幕 → 镜头，后面的门重生成后不回查前面的门（`drama.py:794-799,885`）。
  - 每次重生成都用原始 prompt，前一个门的修正会丢（`:819,885,1089`）。
  - 检查做不了就放行（`:807-810,1142-1156`）：镜头门没有本地副本时连记录都不留（`:849-851`），字幕判读返回的不是 JSON 就按「没有字幕」处理（`domain/media/no_text.py:84-92`）。
  - 到上限只警告（`:815-817,2830-2839`），照样拼进成片（`:2873-2892`）。
  - 改法：做成一个统一循环——跑完全部检查、合并各门的修正再重生成、然后全量重查，总次数封顶；免费的 ffmpeg 镜头门放最前；**字幕没过、或者检查做不了，都判失败，不拼进成片**。
- **[P0] 重复扣费。** 轮询遇到一次 5xx/429 就把原任务判失败（`harness/model/media.py:274-277`）；轮询放弃时的文案里带「网络」二字（`:429-431`）。drama 的 `_TRANSIENT` 把这些都当成暂时性错误（`drama.py:3085-3093`），于是 `_invoke_video` 重新提交（`:764-772`），而原任务其实还在跑、还在计费。`short_video.py:525-529` 也有同样的逻辑。
- **[P0] 已付费的片段会丢，只能重付。** 片段索引要等所有层跑完才写（`drama.py:2785-2792`），而 reuse 只认这份索引（`:725-727`）。调度器 7200 秒超时、Ctrl+C 或崩溃时，整批记录都会丢。改法：每成功一段就增量写一次。
- **[P1] 音色锚点会丢更新、会断档。**

- **[P1] reuse 只按「场 + 镜」匹配**（`drama.py:719-741`）。换了包、换了脸，旧片段照样复用，被标过问题的片段也复用。结果里提示去掉问题段，却没有 `redo` 参数，只能整集重渲（`:2835-2839`）。

### 9. 媒体网关（提交 / 轮询 / 计费 / 并发 / 落地）

- **[P0] task_id 不落盘，钱花了拿不到结果。** `harness/model/media.py:397-449` 没有 try/finally，MODEL_RESPONSE 事件不带 task_id，全仓也没有取回逻辑。/stop（`inputhub.py:118`）、工具超时（`dispatcher.py:92-97`）、200 次轮询到点，都会留下一个仍在远端计费的孤儿任务。改法：提交成功就写一行 pending 台账，加一个取回工具，重跑前先查台账。
- **[P0] 媒体调用不计价。**
  - `config/media_models.yaml` 里 21 个模型都没有 price 字段，只有第 18 行一句注释提到它。所以媒体对金额上限的贡献始终为 0（`domain/functions/media.py:759-767`；`budget.py:165-182,202-209`）。
  - 启动时仍打出绿色 ✓（`main.py:455-460`）。
  - gen_images 只按 jobs 计次，没乘上每项的 n（`gate.py:23-28`）。
  - 日志：图片 240 次、视频 122 次，金额全部为空。
  - 改法：按「元/秒 × 分辨率」填价；闸门先按「段数 × 时长 × 单价」预占额度，完成后按实际结算；没填价就在启动时告警。
- **[P1] 次数上限和一集的规格冲突。** 视频单任务上限 14 次，注释还写着「一集 6 段」（`config/models.yaml:288-295`）；而一集 4 分钟是 16–24 段，每集渲到第 15 段必停，还提示「多半是循环调用」。日志 9b84afed 36 分钟内弹了 40 次。改法：次数上限从 `config/drama.yaml` 推导，按一集一次确认。
- **[P1] 并发控制失效。** 信号量是每次调用各建一个（`media.py:366-367`、`drama.py:117-118`），两批同时跑时并发会翻倍。提交遇到 429 直接判失败、不退避（`harness/model/media.py:225-233`）。改法：在 MediaGateway 里按模态放一个共享信号量；提交遇到 429 退避重试（被拒不扣费，可以安全重试）。
- **[P1] 提交超时重试可能重复建任务。**【推测】读超时（ReadTimeout）也会触发重新提交（`harness/model/media.py:455-467`），drama 层还会再重试一轮，一个镜头最多提交 6 次。请求其实已经送达、只是响应超时的时候，服务端可能已经建好了任务。改法：只对 ConnectError 重试。
- **[P1] 参考素材大面积失效。**【实测】
  - 500 个媒体资产里，约一半只剩已过期的远端链接，而且没有本地副本。
  - `gen_params.local` 记录的 302 个本地文件中，213 个已经不存在，其中 194 个在 `E:\内容测试\images`。这个目录整个不见了，Agent 的回收站里也没有。

- **[P1] 下载失败不重试**（`media.py:773-791`、`domain/output.py:60-69`）。字幕门和镜头门都依赖本地副本，网络一抖，这两道门就被静默跳过。
- **[P1] 海报重犯了 `_localize` 事故。** `domain/functions/poster.py:164-183` 不读本地副本，直接重新下载远端链接，超过 24 小时必然失败；下载成功后又把 uri 改成本地路径，这张图以后再当参考图，就会被 `_not_public` 拒掉。
- **[P2] 模型锁不够灵活。** 采纳换模型后会直接写进快照，短剧链也一起换，没有「只这一次」的选项。有锁时 prefer/tier 参数被悄悄忽略（`media.py:522-523`），所以「先用 fast 档验证方向」和 short_video_produce 的 tier 参数实际都不起作用。
- **[P2] 其他零散问题。**
  - 闸门先计次，再过模型门和参考门（`gate.py:134-138`），被挂起后重新调用会再记一次。

### 10. 抖音 / 广告 / 设计链

实际流程：
1. `list_video_styles` 列出风格。
2. RPA 或 TikHub 抓热点，存成资产。
3. `short_video_brief` 由规划模型出简报；`parse_brief` 把时长夹在风格范围内，口播字数多就往上调。
4. `request_materials` 挂起问你要素材，`resolve_materials` 解析你的回复，再去素材站搜索、下载。
5. `short_video_produce`：已有素材（图片转成静帧）> 同一简报的旧片段 > 并发生成；然后 TTS → 转写并按原稿回贴字幕 → 快切合成。

另有一条老链 `agent video make`，`agent new` 里的「短视频」也走它。

- **[P0] 和短剧一样「失败就重新提交」。** `short_video.py:45,525-529` 直接用 drama 的 `_transient_error`，轮询抖动或遇到 429 时，把已经计费的任务整段重新提交一次。
- **[P0] 选 talking-head（口播出镜）配方，成片没声音、没字幕，出镜画面还被切碎。**
  - 这个配方关了口播（`config/recipes/talking-head.yaml:46`），而字幕以有配音为前提（`short_video.py:565`），所以没有字幕。
  - 快切拼接写死了 `a=0`，把出镜素材的原声丢掉（`domain/media/ffmpeg.py:236`）。讽刺的是，同一个文件第 149 行的注释记着这个坑，但只在另一个拼接函数里修了。
  - `plan_cuts` 轮转取材（`domain/pipeline/cutting.py:130-139`）。实测 40 秒出镜 + 4 段 B-roll，每 5 刀才回到一次出镜。
  - 改法：出镜素材保留原声作主音轨，据此出字幕，不参与轮转。
- **[P0] 广告线的产品身份锁没有通道。**
  - 产线指引要求 gen_video 带产品图（`domain/lines.py:49-53`），但 produce 的生成参数里根本没有参考图（`short_video.py:515-523`）。
  - 产品图如果当素材传，只会被做成静帧剪进去（`:689-700`），这正是 `product-ad.yaml:18` 禁止的。
  - 再加上关口播、关字幕、丢原声，成片里既没有你的产品，也没有声音和字，quality 档的钱白花。
  - 改法：produce 支持按镜头传参考图；补一个按时段叠字的后期步骤。
- **[P1] 快切顺序被打乱，多出的镜头白生成。** `plan_cuts` 按 `i % n` 轮转，刀数只看总时长（`cutting.py:99-106,130-131`）。实测 product-ad 5 个镜头排成 1-2-3-4-5-1，没有以英雄帧收尾；8 个镜头时，第 7、8 镜付了钱，却不出现在成片里。改法：按简报顺序和每镜秒数排刀，镜头数不超过刀数。
- **[P1] 新链丢了配方的风格要点。** `brief_prompt` 只收风格的名称和适用场景（`short_video.py:325`、`domain/pipeline/short_video.py:152-160`）；prompt_hint 和 script_hint 只有老链在用（`recipe.py:180,197`）。ugc-vlog 和 product-ad 最关键的写法要求实际没有传给模型，提示词示例里还写着 seconds:5。
- **[P1] 抖音 RPA 不认关键词。** 抖音侧一律抓热榜页，keyword 没有往下传（`domain/functions/rpa.py:98-107,209-218`、`domain/rpa/interact.py:326-331`），提示词却把这些称作「相关热点」（`domain/pipeline/short_video.py:166`），规划模型会硬套无关热点当出处。改法：抖音侧改用 `douyin_hot_list(keyword)`。
- **[P1] 素材回复解析在中文逗号处不断开**（`domain/pipeline/short_video.py:323`）。实测「第1镜 生成，第2镜 联网找」只解析出第 1 镜；路径后面紧跟逗号时，会把后半句一起吞进路径。
- **[P1] 横屏素材混进来，版权判断失效。**
  - Pixabay 视频搜索不筛方向（`materials.py:320-321`），画布又取第 1 段的尺寸（`ffmpeg.py:219-233`）：轻则出现黑边，第 1 镜是横屏的话整片都变横屏。
  - 用 fetch_media_url、fetch_douyin 下载的他人原片，creator 是 `tool:*`，被 `rights_of` 判成「自己生成」（`domain/assets/store.py:436-437`），机审查不出版权问题。
- **[P1] 复用断链，成片被覆盖。** resolve 用 revise 产生了新 id，而复用只认 `parent_ids[0]`（`short_video.py:655`）：只改一个镜头的素材，所有 AI 镜头都会重新生成。成片名是 `{topic}_{date}` 且直接覆盖写（`recipe.py:123`、`video_edit.py:300-302`），旧资产指向的文件就变成了新内容。
- **[P1] 短剧的引用门会误伤短视频。** 它全局挂在 gen_video 上，按资产库里的角色名、服装名做子串匹配（`app.py:274`、`drama.py:895-916,930`），而 produce 不传 allow_no_refs。【推测】短视频提示词碰巧含这些名字，就会被拦。
- **[P1] 3 秒上限有漏网路径。** 配方里 `cut.enabled=false` 时 cut_max=0，compose 就整段拼接（`recipe.py:112-113`、`video_edit.py:251,268-272`）；角色护照分镜仍按每镜 8 秒设计（`domain/storyboard/breakdown.py:87`）。改法：compose 没传切点时，强制使用全局上限。
- **[P1] 两个 CLI 入口跑不通。**【实测】`agent new` 选短视频时直接调 `video_make(topic=…)`（`interfaces/cli/start_cmd.py:89`），其余参数拿到的是 typer 的 OptionInfo 对象，直接抛 TypeError。`agent rpa collect` 创建的 Agent 没有询问器（`rpa_cmd.py:109`），EXTERNAL 工具一律被拒。
- **[P1] 出片前不报成本。** 简报不限镜头数，也不预估调用次数；produce 本身还被闸门多记 1 次（`short_video.py:164`）。改法：出片前挂起一次，报出镜头数和预计调用次数。
- **[P2] 两条链重复实现。** 成对重复的有：`video_cmd._make` 与 `_fn_short_video_produce`；两个 `_pick_voice`（voice 缺省时一边当成空、一边当成 auto）；`parse_plan` 与 `parse_brief`；`_unwrap_json` 和 CHARS_PER_SECOND 也各有两份。老链还不传真实感档位（`video_cmd.py:191`）。改法：让老链改调这组 functions。
- **[P2] 配方字段对表。**
  - 写了但没人读：tts_model、after_compose、subtitle.source、grounding.source。
  - 代码读了、配方没写：grounding.days。
  - 只有老链在用：grounding.*、output.duration、shots.count、after_script、prompt_hint、script_hint。
  - 被模型锁架空：video_tier。
  - 关了口播的配方仍按口播字数拉长时长（`domain/pipeline/short_video.py:245-251`，实测 15 秒被拉到 20 秒）。
- **[P2] 其他零散问题。**
  - 真实感段每个镜头都无差别追加（`recipe.py:214-216`），可能和 ugc-vlog 要的随拍感冲突。
  - 抽帧查字幕只有短剧链有。
  - 三条视频产线的 content_type 都是「短视频」，所以广告线也会带上 douyin-short，被引导先去抓热点。

设计合理的部分：gen_video 统一包了禁字层，后期烧的是 TTS 转写加原稿回贴的字幕，符合「后期叠字另说」；所有生成都经过 registry、闸门和模型锁，没有直调网关的路径；联网素材只用可商用站点，并登记授权信息。

### 12. 资产底座 / 本地素材 / 文件工具

- **[P0] 模型不经确认就能改自己的规则。**
  - fs_write 属于自动放行的 L-write（`harness/permission/gate.py:41`）。项目根永远在可写范围（`domain/functions/files.py:169`），而 `config/filesystem.yaml:21-34` 的 deny 里没有 config、src、skills、台账和记忆。
  - 可能的场景：用户说「预算不够」，模型直接改 `models.yaml` 的 cost_guard；在 `mcp_servers.yaml` 里加一个任意命令的 server，下次启动就会执行；写一个 priority 100 的 skill；清零台账；伪造 source=human 的记忆。
  - 改法：deny 加上项目下的 `config/ src/ skills/ .venv/` 和 `workspace/{costs,memory,assets,skills_history}`；或者这些路径的写操作一律升为 L-external。
- **[P1] deny 漏掉了真实存在的凭据。** `~/.ssh/id_ed25519_aliyun`、`~/.claude/.credentials.json` 都没被拦，fs_read 读出来就会发给 Kimi。另外 `interfaces/mcp_servers/material_lib.py:167-180` 的 import_material 对源路径没有任何约束。改法：deny 加 `**/.ssh/**`、`**/.claude/**`、`**/*credential*`、`**/AppData/**`；import_material 走同一套 FsPolicy。
- **[P1] 作废的资产仍被当成「最新」取到。** Asset 没有状态字段，查询只按 seq 排序（`domain/assets/store.py:291-312,403-406`）；/rollback 的作废说明只 pin 一轮（`app.py:521`）；面容审查写的 superseded_by 没有读取点。改法：加 status 字段，默认只取 active。
- **[P1] 多进程写资产库不安全。** 各进程的 seq 各算各的，库里已有 61 个 seq 重复（测试进程和真实会话同时写造成的）；两个终端同时开，互相看不到对方的新资产；写一半就崩溃的 JSON 会被静默跳过，资产凭空消失（`store.py:108-124`）。改法：先写临时文件再 os.replace，坏文件要告警；加锁文件，防止开第二个实例。
- **[P2] 其他零散问题。**
  - 本地素材和资产库都不认「第十二集」这种中文数字；缓存 ttl 只有 3 秒，签名缓存形同虚设，每轮都全量重扫。
  - trash 不记原路径（`files.py:212-220`），恢复只能靠猜，也从不清理。
  - fs_import 在线程里建资产，ASSET_CREATED 事件发不出去，流水线会漏接。
  - revise 绕过了落库时的占位符检查（`store.py:242` 对比 `:187`）。
  - 模型换个写法（比如「此处省略…」）照样能把占位符存进去。

### 13. 合规 / 分发 / 数据回流

- **[P1] 整集剧本被当成广告文案查。** 规则按存储类型判断（`domain/functions/compliance.py:48`），而多数整集剧本是 kind=outline 存的，于是被按广告法查极限词（`config/compliance.yaml:21`）。库里约有 100 份「第N集·合规修订版」，台词被按广告法改写，花了钱还伤了台词。改法：机审前先识别整集剧本，按 script 处理。
- **[P1] 待发布包漏掉本地成片。** 打包只看 uri（`domain/distribution/__init__.py:204-214`），而生成媒体的 uri 多是会过期的链接，本地副本不会被拷进包。隐式标识只写在 manifest.json 里，你实际上传的 mp4 本身并不带（`:220-232`）。
- **[P2] 数据回流的门槛太低。** 只要 3 个样本就会提炼成账号层 DATA 记忆（`domain/analytics/__init__.py:213,251`），一条偶然爆款就能改写账号偏好。

### 14. 人机交互（输入框、人审、中断、报错）

- **[P0] 运行中打过字，最终回复可能不显示。**【实测·模拟】输入框每读一行就进出一次 patch_stdout（`interfaces/cli/promptbox.py:194-195`），进度窗又反复开关 Live（`progress.py:120-126,135-139`），两个线程交替改 sys.stdout。结果是回复要么永远不显示，要么和输入框叠在一起。改法：整个会话只进一次 patch_stdout，Live 关掉 redirect；或者进度改用 bottom_toolbar 显示。
- **[P0] 后台提问会抢走输入**（见第 8 节）。
- **[P1] /stop 不清排队**（`inputhub.py:115-119,167-172`；`main.py:947-949`）。如果排队里有「再渲第 3 集」，停完会立刻开下一轮，继续花钱。
- **[P1] 人审决策口有两个坑。** 在决策口按 Ctrl+C 产生的「/stop」会被当成打回理由，存进记忆；按 Ctrl+D 会直接让 chat 崩溃（`main.py:290-311,345-350`；`promptbox.py:198-199`）。
- **[P1] 人审时看不到图片和视频。** 媒体候选的 content 为空，决策面板只打印 `content[:1500]`（`main.py:280`），给你的就是一个空框，既没有链接，也没有本地路径；标题 `[as_x|image|v1]` 还被 rich 当成标签吞掉了。改法：图片/视频显示 uri 和本地路径，加一个「o 打开」键。
- **[P1] 任何未捕获的异常都会退出 chat。** 模型回复被当作 rich markup 解析（`main.py:247,280`），只要文本里含 `[/]` 或 `[/budget allow 50]` 就会抛 MarkupError；挂起的人审只存在内存里（`loop.py:103`），重启后被补成「已中断」，也不告诉你。改法：输出前先转义；每轮套一层 try/except，出错时报错、存快照、回到提示符。
- **[P1] /budget reset 名不副实。** 它只清进程内的计数，却提示「已清零」（`main.py:769-772`；`budget.py:281-284`），而停机提示正是把它当出口推荐的（`app.py:378`）。
- **[P2] 命令表和实现对不上。** /help 没实现；/line 不在表里；/stat 的说明和实际输出不符；拼错的 /xxx 会原样发给模型。改法：用同一张表同时驱动补全和分发。
- **[P2] 可观测性有缺口。** /stop、预算和权限放行、调度前的拒绝、质检门的判定都不发事件，复盘时只能反推。sessions replay 不显示 decided_by，分不清哪些是 /auto 自动采纳的。
- **[P2] 分层问题。** `_chat` 是一条近 400 行的 if 链，自动放行、/auto 联动、断网重试、产物目录持久化这些业务规则都写在 CLI 里，将来换 Web 台就得重写。改法：在 app 层抽出一个 AgentSession。
